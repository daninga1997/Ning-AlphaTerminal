# 模拟交易列表与手动平仓设计

## 目标

在现有仅限详情页的模拟交易记录基础上，提供一个统一的模拟交易台账页面，并允许用户对仍在进行中的模拟交易按当前服务器报价手动平仓。该能力只记录和复盘模拟结果，不连接券商、不提交订单、不改变策略、分钟 K 线或自动刷新行为。

## 方案选择

采用独立的服务端聚合方案：

- 扩展 `PaperTrade` 状态为 `manual_closed`，保留现有 `open`、`take_profit`、`stop_loss`、`expired`。
- 由一个列表服务对全部未结算记录先进行既有自动结算，再返回筛选、排序和统计所需数据。
- 手动平仓只提交交易记录 ID；服务端再次读取实时真实报价，以该报价作为卖出价写入结算结果。

不采用前端自行汇总或提交卖出价的方案，避免页面只显示局部记录、报价被篡改或不同页面统计不一致；也不复用 `TradingPlan`，因为模拟交易的生命周期独立于计划记忆。

## 数据与状态

`PaperTradeStatus` 增加 `manual_closed`。所有已结算状态为：`take_profit`、`stop_loss`、`expired`、`manual_closed`；`open` 是唯一进行中状态。

手动平仓写入：

- `status=manual_closed`
- `exitPrice`：服务端在操作时取得的真实报价
- `exitTime`：服务端结算时间
- `returnPercent`：`(exitPrice - entryPrice) / entryPrice * 100`，保留两位小数
- `settlementReason=manual_closed`
- `openKey=null`，从而允许该股票再次模拟买入

若实时真实报价不可用，平仓请求失败且记录保持 `open`；不使用缓存价、Mock 价或客户端传入价格替代。

## API

- `GET /api/paper-trades?status=all|open|closed&sort=entryTime|returnPercent|exitTime`
  - 无 `code` 时返回全部记录、经过自动结算后的统计与当前筛选结果。
  - 有 `code` 时保留详情页现有按股票查询能力。
- `POST /api/paper-trades`
  - 保持现有模拟买入逻辑，客户端仅提供股票代码。
- `POST /api/paper-trades/[id]/close`
  - 只接受记录 ID，不接受卖出价格或状态。
  - 仅能关闭 `open` 记录；已结算记录返回冲突，不会覆盖原结果。

错误响应沿用安全错误码，不返回上游异常、请求头或报价原始内容。

## 页面与交互

### 模拟交易列表 `/paper-trades`

在左侧导航增加“模拟交易”入口。页面包括：

- 标题、模拟数据说明与记录数量。
- 状态筛选：全部、进行中、已结算；“已结算”聚合四种已结算状态。
- 排序：买入时间、卖出时间、收益率。
- 交易记录：股票名称/代码（链接至 `/stocks/[code]`）、买入价/时间、卖出价/时间、收益率、状态。
- 统计：总交易数、已结算胜率、已结算累计收益率、已结算平均收益率。由于没有仓位和资金金额，累计收益率定义为各笔已结算 `returnPercent` 的算术和，而非账户资产回报。

没有记录时显示明确空状态；没有已结算记录时，统计收益率和胜率显示 `--`，避免把未实现盈亏当作已实现结果。

### 股票详情页

仅当存在 `open` 模拟交易时显示“手动平仓”按钮。点击后先显示二次确认，确认文案说明将以当前服务器报价结算且无法恢复为进行中；确认后调用专用平仓 API。成功后刷新记录，显示手动平仓的卖出价、卖出时间和收益率；按钮消失，模拟买入按钮重新可用。

## 验收与测试

- 迁移只扩展枚举，不重置或删除 SQLite 数据。
- 列表页可访问，筛选、排序和统计与数据库记录一致。
- 手动平仓必须使用服务端真实报价；报价不可用时不更新记录。
- 仅 `open` 记录可见并可执行手动平仓；重复请求不改变已结算结果。
- 手动平仓后允许再次模拟买入。
- 详情页、列表页和 API 不影响现有分钟 K 线及其自动刷新。
- 覆盖服务、API、页面交互测试，并通过 TypeScript、lint、测试与构建。
